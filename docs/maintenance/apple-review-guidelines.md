# Apple App Review Guidelines for Safari Extensions

Releasing a Safari Web Extension requires submitting a standard native macOS App that bundles the web extension inside it. The Apple App Review team evaluates this package exactly as they would review any native Mac application.

Because the Safari Xcode generation tools (`xcrun safari-web-extension-converter`) handle the core architecture, you generally do not need complex native `Info.plist` modifications. However, there are strict guidelines you must follow to avoid rejection.

## 1. Set an App Category

Apple requires all Mac apps to declare exactly what kind of app they are.

1. Open `safari/WebToMarkdown.xcodeproj` in Xcode.
2. Select the **WebToMarkdown (macOS)** target.
3. Open the **General** tab.
4. Under **Identity**, select an **App Category** (e.g., `Productivity` or `Utilities`).

*(This automatically injects the `LSApplicationCategoryType` key into Xcode's generated internal `Info.plist`, which prevents immediate automatic rejection during the App Store Connect upload stage).*

## 2. Provide Native Apple Icons 

**This is the #1 reason for early rejection.** App Review will immediately reject your app if they see the placeholder silhouette or gear icons generated by the starter template.

1. Open Xcode and navigate to the `Shared (App)/Assets.xcassets` folder.
2. Drag and drop properly sized image assets for:
    - **AppIcon**: The icon for the Mac app itself.
    - **LargeExtensionIcon**: The icon shown in Safari's extension preference pane.
    
*Note: Your `manifest.json` icons primarily cover the Safari browser toolbar; these native Apple assets are explicitly for the macOS operating system environment.*

## 3. The "Wrapper" App Experience

When a user downloads the extension from the Mac App Store, it is placed in their `Applications/` folder. Double-clicking it opens a native Mac window.

Apple fully supports and accepts the default UI generated by the `xcrun` command. The standard Swift UI window that simply displays your app icon, the title "WebToMarkdown", and a button to **"Quit and Open Safari Preferences"** is exactly the pattern Apple expects for web extension containers. 

You do not need to build out complex native application features.

## 4. Verify the App Sandbox Entitlement

Apps distributed through the Mac App Store strictly require the App Sandbox.

1. In Xcode, go to the **macOS App Target** -> **Signing & Capabilities**.
2. Verify that the **App Sandbox** capability is enabled. 
3. *Note: `xcrun` usually adds this by default, but its accidental removal will guarantee an App Store rejection.*

## 5. App Store Connect Metadata

When submitting the finalized `.pkg` / `.app` via Xcode to App Store Connect, you must provide:

- **Screenshots:** You need screenshots of the Mac wrapper application window, *and* screenshots showing the extension actively running inside Safari on a Mac.
- **Privacy Policy & Support URLs:** Apple strictly requires robust website links for user privacy policies and technical support forms/portals.
- **Privacy Declarations (Nutrition Labels):** You must answer data collection questions. If your extension operates entirely locally without sending data to an external server, complete the form by declaring **"Data Not Collected"**.
- **Review Notes:** In the "App Review Information" section, explicitly explain to the reviewer how to test the extension. 
   - *Example:* "Open Safari, navigate to a documentation site like react.dev, click the extension icon, and observe the page content successfully converted and copied as Markdown."

## Permissions & Manifest

Because this project utilizes a `manifest.json` (Manifest V3) extension architecture, the host macOS system and Safari sandbox defer to and trust the permissions declared in your JSON (such as `activeTab` or `clipboardWrite`).

Do **not** try to place Apple-native privacy usage descriptions in `manifest.json`; that file is for browser extension metadata and permissions.

You do not need to add traditional native system privacy usage descriptions (e.g., camera usage, file structure access) to the `Info.plist` unless the native Swift wrapper app itself executes code requiring them. Apple-native privacy metadata, when needed, belongs in the Safari wrapper project (for example `PrivacyInfo.xcprivacy`).
